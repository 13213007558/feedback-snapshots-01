# SRP 登录防账号枚举设计（基于 pysrp 纯 Python 后端）

## 威胁模型

若服务端对“未注册账号”直接拒绝下发挑战（返回空、错误码或立即关闭连接），
攻击者只要观察“有没有挑战”即可批量枚举账号是否存在。本模块保证：**任何身份
都会收到一份结构相同的 SRP 挑战**，未知身份拿到的是无法登录的伪记录
（decoy）挑战。

实现位于 `srp/server/srp_server.py`，仅依赖 `srp._pysrp`（纯 Python），不使用
ctypes / C 扩展。

## 设计要点

### 1. 真实与伪记录共用同一公开参数集

`POLICY_HASH_ALG = SHA256`、`POLICY_NG_TYPE = NG_2048` 对真实记录与伪记录完全
一致。盐长度固定为 `SALT_BYTES = 16`，公开值 `B` 都由同一个
`Verifier.get_challenge()` 产生，长度等于模数字节长度（256 字节）。两条路径
返回的都是 `(salt: bytes, B: bytes)`，不存在某一分支返回 `None` 的公开差异
（`A % N == 0` 的 SRP-6a 安全检查对两条路径同样返回 `(None, None)`）。

### 2. 伪盐与验证材料由服务端秘密 + 身份确定性派生

`SrpServer._decoy_record` 使用部署时注入的 `server_secret`（要求 ≥32 字节，
永不上线、不参与真实记录）作为 HMAC 密钥：

- 伪盐：`HMAC(secret, "srp-decoy-salt" || I)` 截断到 16 字节；
- 伪私钥 `x`：`HMAC(secret, "srp-decoy-x" || salt || I)`；
- 伪验证元：`v = g^x mod N`，与真实验证元用**同一个模幂原语**生成，因此是
  合法群元素，`B = k*v + g^b mod N` 的格式与真实记录无法区分。

确定性派生使同一身份每次得到相同伪记录（不会因“每次查询结果都变”而被直接
识别），HMAC 同时绑定服务端秘密与身份：不知道秘密的攻击者无法预测或预计算伪
记录，两个身份在无 HMAC 伪造能力下不可碰撞。结果按身份缓存并加锁，伪握手不
写任何全局可变状态。

### 3. 未知账号永远无法完成业务认证

`HandshakeSession` 携带 `is_decoy` 标志。`verify_proof` 即使在密码学比较偶然
通过时，也会因为 `is_decoy` 为真而强制返回 `None`；伪记录背后不存在任何真实
口令，因此业务认证状态恒为未通过。

### 4. 并发真实账号不受伪握手影响

每次 `begin_handshake` 都创建独立的 `Verifier` 与 `HandshakeSession`，伪记录
缓存是只读复用（同一 `(salt, v)` 可被任意会话安全共享，等价于多个真实用户
共用一份注册数据）。真实账号的会话密钥、证明互不共享。测试
`test_concurrent_real_handshakes_isolated_from_decoys` 以 8 线程 ×25 次交替
握手验证：真实账号始终成功、伪账号始终失败、无 HAMK 泄漏、无异常。

### 5. 错误日志不暴露记录是否存在

所有失败（真实账号口令错误、伪账号任意猜测、畸形 `A`、重放）只输出固定字符串
`SRP verification rejected`，不含用户名、盐、记录类型或分支名。测试
`test_rejection_logs_are_uniform` 断言日志集合只有这一条消息，且不含
`alice`、`mallory`、`decoy`、`real`、`salt` 等字样。需要区分指标统计时应使用
进程内计数器，而不是可被外部观察的差异化日志。

## 测试如何比较两条握手路径

`srp/server/test_anti_enumeration.py` 用固定账号（真实 `alice` / 未知
`mallory-never-registered`）和记录型密码学调用（`CryptoTracer` 包装
hash、HMAC、模幂 `pow`、OS RNG 四类原语）比较：

| 检查项 | 真实路径 | 伪路径 | 结论 |
| --- | --- | --- | --- |
| 公开盐长度/类型 | 16 字节 bytes | 16 字节 bytes | 形状一致，值不同 |
| 公开 B 长度 | 256 字节 | 256 字节 | 形状一致，值不同 |
| 原语操作类别序列（预热后） | 26 项 | 完全相同的 26 项 | 类别与次数一致 |
| 最终 HAMK / 认证 | 成功 | 恒 `None` / 失败 | 伪账号不可登录 |
| 畸形 `A % N == 0` | `(None, None)` 后拒绝 | 完全相同 | 协议安全检查一致 |
| 失败日志 | 固定一条 | 固定一条 | 无身份/分支信息 |

冷启动（首次查询某未知身份）会额外出现两次 HMAC 派生调用；`prewarm_decoy`
可在服务启动时预热，使线上查询全部走“热”路径。

## 这些检查能排除哪些枚举信号

1. **有无挑战 / 不同错误码 / 连接行为差异**：两条路径都返回同形 `(salt, B)`。
2. **消息格式差异**：盐与 B 的长度、编码、类型完全一致，参数集相同。
3. **操作类别差异**：预热后 hash / HMAC / 模幂 / RNG 的调用序列与次数一致，
   攻击者无法用“服务端有没有做某类运算”区分记录类型。
4. **认证结果侧信道**：真实账号口令错误与伪账号任意猜测返回同一种失败。
5. **日志侧信道**：统一固定日志，不记录记录是否存在。
6. **跨会话状态侧信道**：伪握手不污染真实账号会话，并发结果稳定。

## 仍需部署测量的时间侧信道（不能凭几次耗时相近宣称恒定时间）

结构性检查证明的是“代码路径与消息同构”，**不是**统计意义上的恒定时间。
Python 整数运算、字典、内存分配本身就是数据依赖、变长的，以下信号仍需在真实
部署环境中测量：

1. **首次接触伪记录的派生开销**：冷查询多出两次 HMAC（及缓存未命中）。应在
   启动时用 `prewarm_decoy` 预热全部常见身份，或对身份空间做批量预派生。
2. **存储命中与未命中的查找耗时**：`constant_time_get` 已用 HMAC +
   `hmac.compare_digest` 做定长比较并遍历快照，但遍历次数随注册用户数变化、
   字典与内存访问仍有数据相关耗时，需要在线测量分布，而非只看均值。
3. **模幂/哈希的数据依赖耗时**：`pow(base, exp, N)` 的耗时随指数比特、操作数
   前导零长度变化；`long_to_bytes`、大整数分配也是变长的。伪与真实验证元的
   数值不同，单次耗时天然有差。
4. **GC、调度、网络与日志 I/O 抖动**：解释器垃圾回收、线程调度、TCP 分段与
   日志写入都会叠加到端到端延迟上。

### 部署测量建议

- 对“真实账号正确口令 / 真实账号错误口令 / 未知账号”三类请求各采集**数千次
  以上**端到端延迟，记录中位数、分位数（p50/p95/p99）、方差与完整分布，而不
  是只比较几次平均值。
- 使用双样本检验（如 Mann–Whitney U / 对分位数做置信区间）评估两组分布是否
  可区分；必要时做可区分性/分类器实验（用延迟训练二分类器， chance-level
  才算通过）。
- 在与生产同构的硬件、负载、语言运行时（含 GC 调优）下测量，并覆盖冷/热缓存、
  不同并发度。
- 工程缓解：预热伪记录、统一填充与固定消息长度、对失败路径补齐等量工作、必要
  时引入固定延迟预算（注意固定延迟只能抬高门槛，不能替代分布测量）。
- 结论口径：只能声称“公开消息与操作类别不可区分，且延迟分布在 N 次样本下未
  观察到统计可区分性”，**不能**仅凭几次耗时相近就宣称恒定时间。
