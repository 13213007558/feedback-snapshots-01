# 同一份 python-doubleratchet 存档被两个进程恢复：能否水平扩容？

结论先行：**不能**。两个进程都能从同一快照发出密文，只说明 `encrypt_message` 是纯本地、无外部协调的运算；
它不构成安全可用的水平扩容。Double Ratchet 的安全前提是“每条发送链只有一个按序推进的写者”，
而把同一持久化状态复制给两个进程，等于在链密钥派生处制造了一个库自身无法察觉的分叉。

配套可运行演示：`demo/fork_demo.py`（基于本仓库 python-doubleratchet 1.3.0，`.venv/bin/python demo/fork_demo.py`）。
脚本只打印 SHA-256 短指纹、公开头编号和异常类型，不输出任何真实私钥、消息密钥、IV 或明文。

## 1. 分叉是怎么发生的：发送链、消息编号、状态导出

### 1.1 发送链密钥派生是确定性单步推进

发送链是一条 KDF 链。每次发送（`kdf_chain.py::step`）：

```
输出 = KDF(当前链密钥, 消息链常量)         # 取后 32B 作为消息密钥 MK
新链密钥 = 输出的前 32B；链长度 length += 1
```

链密钥只依赖“上一个链密钥 + 常量”，**没有随机数、没有进程身份、没有存储代次**。
因此两个从同一快照恢复的副本，其链密钥逐字节相同；各自再走一步，得到的也是同一个消息密钥。

### 1.2 消息编号来自链长度，分叉后编号重叠

`diffie_hellman_ratchet.py::next_encryption_key` 构造的公开头 `Header` 为：

- `ratchet_pub`：当前 DH  ratchet 公钥（快照里固定，分叉两侧相同）；
- `previous_sending_chain_length`：上一条发送链长度；
- `sending_chain_length`：派生**之前**的链长度，即该消息在链上的编号 `N`（首条为 0）。

两个副本从同一 `length` 起步，于是各自的“下一条消息”携带**完全相同的公开头**
（演示场景 1：两侧 `ratchet_pub` 与编号都相同），并用同一个 MK 加密不同内容。

### 1.3 状态导出无法区分两个写者

`DoubleRatchet.json` / `from_json` 只做状态的序列化与还原。两个副本在各自发送一步后，
由于输入相同、KDF 确定，导出的新状态又变得逐字节相同（演示场景 1 末尾两个状态指纹一致）。
也就是说：**存档里不存在“谁是合法写者”“这个状态被恢复过几次”“它基于哪个存储代次”这类字段**。
分叉对库完全不可见，无法靠比对两份 JSON 判断哪份权威。

### 1.4 为什么不能用“密文是否相同”判断安全

- 同一 MK、不同明文，密文当然不同——这只反映明文不同，不代表密钥不同。
- 更严重的是推荐 AEAD（`aead_aes_hmac.py`）用 AES-256-CBC + HMAC，其 IV 不是随机的，
  而是由 MK 经 HKDF **确定性派生**。分叉消息共用 MK，就意味着共用 `(密钥, IV)`：
  这是 CBC 两次性填充（two-time-pad）/ 密钥复用，会泄露两段明文的异或关系，属真实密码学危害。
- 演示场景 4 用一个**独立随机探针密钥**（非会话材料）证明该确定性：同一密钥加密两个明文，
  首个密文块相同，证明 IV 随密钥固定；脚本不打印任何真实 IV 或密钥。

## 2. 正常对端看到的事实（接收顺序、公开头、状态冲突）

对端（Bob）用 `(header.ratchet_pub, header.sending_chain_length)` 定位接收链上的消息密钥
（`double_ratchet.py::decrypt_message` 与 `diffie_hellman_ratchet.py::next_decryption_key`）。
当 `header.sending_chain_length < 接收链长度` 时抛 `DuplicateMessageException`。

固定同一初始状态，让两个副本各发一条不同内容，交给一个正常对端（演示场景 2、3）：

- **接收顺序无关**：无论先 A 后 B 还是先 B 后 A，第一条被接受，第二条必然 `DuplicateMessageException`。
  其中一个业务负载永久不可达，且这是静默的数据丢失，不会有“两条都到了”的信号。
- **使用的公开头**：两条消息的 `ratchet_pub` 与编号 `N` 相同，对端把它们识别为同一链上的同一序号。
- **状态冲突**：对端接收链在接受第一条后前进，第二条被判定为“派生点早于当前位置”的重放；
  解密失败时库会丢弃克隆、保持对端状态不变，但发送侧两个副本的链已经各自独立漂移，无法自动收敛。
- **对照基线**：单一写者下编号严格递增；乱序（先发后到）由“跳过消息密钥”机制正常容纳
  （场景 3：m1 先到、m0 后到均 ACCEPTED）。该机制只容忍**同一条链上的乱序**，不容忍两条分叉链抢占同一编号。

## 3. 三种部署形态对比

| 形态 | 发送链写者 | 库能否独立保证正确 | 适用与代价 |
| --- | --- | --- | --- |
| 单写者（会话亲和/分片） | 恰好一个进程持有并推进某会话 | 能，符合算法前提 | 最稳；按会话做一致性哈希或粘性路由，故障时需在确认旧写者停机后再接管 |
| 带代次的外部事务（fencing + CAS） | 逻辑上单写者，由存储层强制 | 不能，需外部存储配合 | 多进程可取用，但每次“加载-加密-保存”必须在带代次的原子事务内，CAS 失败即作废并重租 |
| 每端独立会话（每进程各自 ratchet） | 每个会话各自一个写者 | 能 | 真正的水平扩展路径：进程与会话一一对应，对端按会话区分；代价会话数随进程数增长 |

直接“多进程共享同一份存档、各自读写”不在上表，因为它违反单写者前提，没有安全配置。

## 4. 库自身无法证明的持久化事实

python-doubleratchet 的边界是内存中的 ratchet 状态与 JSON 序列化。下列事实都发生在库之外，
库的 API 没有任何机制可以证明或强制：

1. 某个会话当前是否只有一个写者；
2. 一份存档被反序列化、复制、并发挂载了多少次；
3. “读取快照 → 加密 → 写回状态”是否作为一个原子事务执行；
4. 写回时所基于的状态是否仍是当前最新版本（丢失更新/陈旧写）；
5. 持久化是否在消息投递之前落盘（崩溃后可能重用尚未提交的发送状态）；
6. 两份相同 JSON 中哪一份代表权威写者。

库提供的 `DuplicateMessageException`、跳过消息密钥上限、DoS 阈值等，都是**接收侧的事后检测与自保护**，
不能阻止发送侧分叉，也不承担分布式一致性职责。因此安全性必须由接入层的持久化与并发控制来补足。

## 5. 阻止复用旧发送状态的最小接入方案

最小可用控制：在存储层为每个会话记录维护一个单调递增的 `generation`，
用“租约 + 比较并交换（CAS）”把发送操作收敛为单写者。演示场景 5 的 `GenerationStore`：

1. 进程发送前 `lease()` 取出 `(generation, state)`；
2. 在该副本上 `encrypt_message`；
3. 用 `compare_and_swap(expected_generation, new_state)` 原子提交：仅当存储仍是该代次时才写入并把代次 +1；
4. CAS 失败说明已有更新的写者提交——**丢弃本副本的发送状态与密文，重新 `lease` 最新状态后再试**，
   从而在消息到达对端之前就拦住陈旧发送状态。

工程化要点：

- CAS 需落到真正提供原子条件写的系统（关系库 `UPDATE ... WHERE generation=?`、带版本号的 KV、Zookeeper
  zxid/etcd 版本号等）；进程内锁不足以覆盖多节点。
- 顺序约束应为“先提交状态、再投递密文”（write-ahead），避免崩溃后重用未提交的链密钥。
- 租约应配合 fencing token 在下游（如消息队列）也拒绝旧 token，防止旧写者在网络分区后仍投递。
- 需要真正多活时，改用“每端独立会话”，而不是复制同一发送链。

## 6. 部署约束清单

- 一个 Double Ratchet 会话的发送链在任一时刻只允许一个写者；禁止把同一存档分发给多个活跃发送进程。
- 恢复/接管前必须确认前任写者已停机或其代次已失效；接管点之后不得再使用旧副本发送。
- 任何多进程取用都必须经由带代次的原子 CAS 事务，并在 CAS 失败时作废本地状态、重新租约。
- 状态持久化先于消息投递；序列化载荷（含链/消息密钥与私钥）必须静态加密并严格访问控制。
- 诊断只记录公开头编号、代次、异常类型与状态/密钥指纹（如本演示的短哈希），
  不写入完整私钥、消息密钥、IV 或明文。
- 不要把“能产出不同密文”当作健康指标；应监控同一会话出现相同 `(ratchet_pub, 消息编号)` 的发送，
  以及对端 `DuplicateMessageException` 速率，作为分叉/重放告警。
