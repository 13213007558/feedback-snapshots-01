= Documentation for Internal Request Permissions Feature

The internal request permissions feature adds an explicit permission
registry for internal requests.  It is intended for applications where
batch jobs or other internal callers have different levels of privilege.
Each approved caller identity (a principal) is registered for the
internal request operations it is allowed to perform.

This feature requires the internal_request feature.  When enabled, every
internal request must include a +:principal+ option, and the principal
must be registered for the operation being performed.

  plugin :rodauth do
    enable :verify_account, :internal_request_permissions

    internal_request_permission :account_reader,
      :account_exists?, :account_id_for_login

    internal_request_permission :account_notifier,
      :verify_account
  end

  App.rodauth.account_exists?(principal: :account_reader, login: 'foo@example.com')
  App.rodauth.verify_account_resend(
    principal: :account_notifier, account_login: 'foo@example.com')

A principal can be allowed an operation in either of two ways:

Operation name :: Register the specific internal request method, such as
                  +:account_exists?+ or +:verify_account_resend+.
Feature name :: Register the feature that owns the internal request
                methods, such as +:verify_account+.  This allows all
                internal request methods provided by that feature.

Permissions are registered at configuration time using
+internal_request_permission+, and can be removed using
+remove_internal_request_permission+.  A principal that is not registered
is not allowed to perform any internal request.  A registered principal
with no operations is also not allowed any operations.

== Enforcement Point

Authorization occurs in the internal request entry point before Rodauth:

* resolves +:account_id+ or +:account_login+
* binds remaining options to request parameters
* runs any route hooks, including +before_rodauth+ and feature-specific
  route hooks
* performs the feature operation

A denied call therefore cannot read an account, deliver email, write
tokens, or trigger business event hooks.  Normal Rack requests are not
affected.  They continue to use the standard Rodauth routes and existing
CSRF and hook processing.

== Exception

Unauthorized internal requests raise Rodauth::InternalRequestNotAuthorized,
a subclass of Rodauth::InternalRequestError.  It provides these
additional attributes:

principal :: The principal supplied for the request, or nil if none was supplied.
operation :: The internal request operation (a symbol, such as +:account_exists?+).
feature :: The feature that owns the operation (a symbol, such as +:verify_account+).
denial_reason :: +:no_internal_request_principal+ when the request did not include a principal, or +:operation_not_allowed+ when the principal is not registered for the operation.

== Caller Attribution

Application hooks can identify the approved caller during an internal
request using:

internal_request_authorized? :: Whether the current internal request was approved.
internal_request_permissions_principal :: The approved principal, or nil for normal Rack requests.
internal_request_permissions_operation :: The approved operation, or nil for normal Rack requests.
internal_request_permissions_feature :: The feature owning the operation, or nil for normal Rack requests.

These methods return false or nil for normal Rack requests, and for
internal requests that were denied.

When the +audit_logging+ feature is enabled, audit log metadata for
business events generated by an approved internal request includes the
principal and operation.  The metadata keys can be changed with
+audit_log_internal_request_principal_key+ and
+audit_log_internal_request_operation_key+.

== Auth Methods

internal_request_authorized? :: Whether the current internal request was approved.
internal_request_operation_allowed?(principal, operation, feature=nil) :: Whether the principal is allowed the operation or owning feature.
internal_request_permission(principal, *operations) :: Register the allowed operations (or owning features) for the principal.  This is also available as a configuration method.
internal_request_permission_for(principal) :: Return the registered operations for the principal, or nil if the principal is not registered.
internal_request_permissions_allowed? :: Whether the current request is an approved internal request.
internal_request_permissions_enabled? :: Whether the internal_request_permissions feature is enabled.
internal_request_permissions_feature :: The feature owning the approved operation, or nil.
internal_request_permissions_operation :: The approved operation, or nil.
internal_request_permissions_principal :: The approved principal, or nil.
remove_internal_request_permission(principal) :: Remove the registration for the principal.
