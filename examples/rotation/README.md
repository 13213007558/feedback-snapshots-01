# 认证器轮换示例（基于 ROTP）

更换动态口令认证器时，新秘密生成后**不会**立即顶替旧秘密，而是进入
三态版本模型，确认完成后才切换：

| 状态 | 普通登录 | 授权发起轮换 | 确认轮换 |
| --- | --- | --- | --- |
| `pending`（待确认） | 否 | 否 | 是（必须用该版本自己的秘密对应的口令） |
| `active`（已启用） | 是 | 是 | 否 |
| `revoked`（已撤销） | 否 | 否 | 否（终态，永不复活） |

规则要点：

- 发起轮换需当前 `active` 版本的口令授权；`pending` 与 `revoked` 无此权限。
- 确认成功时，新版本变为 `active`，其余所有版本（旧 `active` 与其他
  `pending`）在同一临界区内一并撤销。
- `revoked` 是终态：双浏览器并行时迟到的挑战、确认后的重复提交、
  用户取消后的再次确认，都无法让已撤销版本重新启用。
- 审计日志只记录版本号与状态迁移；秘密与 provisioning URI（二维码）
  只在注册响应中返回给调用方一次，绝不写入日志。

运行：

```sh
ruby examples/rotation/demo.rb
```

演示使用内存存储与可推进时钟，依次走完：成功轮换、双浏览器并行 +
迟到挑战 + 重复提交、用户取消，并逐步打印每个版本当前可用于什么操作。
