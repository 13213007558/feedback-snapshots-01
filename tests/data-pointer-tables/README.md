# pointer-tables.exe

A hand-built, minimal .NET module used to verify member ownership when
metadata uses the pointer tables.  The file is generated by
`make_sample.py`; both are checked in so the layout can be reviewed and the
binary reproduced byte-for-byte.

Generate it from the repository root:

```shell
python tests/data-pointer-tables/make_sample.py
```

## Why this sample exists

Method/field/parameter ownership must not be derived from the physical order of
the `Field`, `MethodDef`, and `Param` tables.  With uncompressed metadata
(`#-`), the owning tables' `FieldList`, `MethodList`, and `ParamList` columns
index the pointer tables (`FieldPtr`, `MethodPtr`, `ParamPtr`), and only the
pointer rows index the target tables.  The pointer values may be out of order,
repeated, or invalid.  This sample exercises all of those cases and can be
checked by hand against the tables below.

The `#-` stream is used instead of `#~`, so the sample also covers
non-compressed metadata (we do not run the CLR, so the format is otherwise
valid).

## Expected ownership (hand-computed)

The list column of an owner starts a run, and the run ends just before the
next owner's start.  The final owner runs to the end of the pointer table.

### Fields (via `FieldPtr`)

| Owner | Pointer rows | Field rows | Field names |
|---|---|---|---|
| `<Module>` | 1 | 1 | `f_alpha` |
| `OwnerA` | 2..3 | 2, 2 | `f_beta`, `f_beta` |
| `OwnerEmpty` | (empty: start 4, next owner start 4) | | |
| `OwnerShared` | 4 | 3 | `f_gamma` |
| `OwnerInvalidPtr` | 5..6 | 0 (invalid), 99 (out of range) | (both skipped) |
| `OwnerDecreasing` | (empty: start 7, next owner starts at 5) | | |
| `OwnerTail` | 5..6 | 0 (invalid), 99 (out of range) | (both skipped) |
| `OwnerFinal` | 6 (final owner: runs to the last pointer row, 7) | 99 (out of range), 2 | `f_beta` |

`OwnerA` and `OwnerShared` share `FieldPtr` row 3 (which points at `f_beta`
twice); this must stay two owner-local entries, not a global field map.

### Methods (via `MethodPtr`)

| Owner | Pointer rows | MethodDef rows | Method names |
|---|---|---|---|
| `<Module>` | 1 | 3 | `m_three` |
| `OwnerA` | 2..3 | 1, 4 | `m_one`, `m_four` |
| `OwnerEmpty` | (empty: start 4, next owner start 4) | | |
| `OwnerShared` | 4 | 2 | `m_two` |
| `OwnerInvalidPtr` | 5 | 1 | `m_one` |
| `OwnerDecreasing` | (empty: start 7, next owner starts at 6) | | |
| `OwnerTail` | 6 | 4 | `m_four` |
| `OwnerFinal` | (empty: final owner starts at 7, past the last pointer row) | | |

### Parameters (via `ParamPtr`)

`MethodDef` rows are the final owners of their own `ParamList` column, so each
run ends at the next method's `ParamList` value.

| Method | ParamList | Pointer rows | Param rows | Param names |
|---|---|---|---|---|
| `m_one` | 1 | 1 | 2 | `p_second` |
| `m_two` | 2 | 2..3 | 1, 3 | `p_first`, `p_third` |
| `m_three` | 4 | (empty: start 4, next method start 4) | | |
| `m_four` | 4 (final method: runs to the last pointer row, 6) | 4..6 | 2, 1, 99 (out of range) | `p_second`, `p_first` |

## Invalid data is never reattributed

- `FieldPtr[5] = 0` and `FieldPtr[6] = 99` are invalid and are skipped; they
  must not be clamped to row 1 or row 3.
- `ParamPtr[6] = 99` is out of range and is skipped.
- `OwnerDecreasing` encodes a decreasing run start; its run is empty, not
  "the rest of the table".  `OwnerFinal` is the final field owner, so its
  field run reaches the end of `FieldPtr`, while its method start is past the
  end of `MethodPtr` and therefore empty.
- `OwnerEmpty` and `OwnerShared` both start at pointer row 4; that encodes an
  empty run for `OwnerEmpty`, not shared ownership.

Warnings are logged for each of these cases.

## List column widths

With uncompressed metadata, the list columns index the pointer tables when
those are present, so their width must accommodate the pointer table's row
count as well as the target table's.  For example, a module with 70,000
`FieldPtr` rows stores `TypeDef.FieldList` as a 4-byte index.  dnfile selects
the width from both tables; see `test_list_columns_are_wide_enough_for_pointer_tables`.
